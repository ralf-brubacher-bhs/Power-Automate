## 1. Purpose

- **What it does:** every day at 9:50 (US Eastern time) it queries the Home Health *Notice of Admission* (NOA) Power BI semantic model and sends an email with a summary of NOAs approaching their due date, a table by branch, and an Excel attachment with patient-level detail.
- **Who receives it:** the distribution list for all Home Health branch office staff (To) and five people from leadership, billing and BI (CC).
- **Business decision it supports:** getting each branch to submit its NOAs on time. A late NOA incurs a daily penalty of 1/30 of the payment for every day it is late, so the email puts overdue and due-today cases first (deadline: 12:00 PM ET).
- **Pattern used:** **C, DAX query** (three "Run a query against a dataset" actions) combined with **an Excel file generated by Office Scripts** as the attachment. Criteria: General guide §1 and §2.4.
- **Would a native subscription be enough?** No. The email includes business instructions, a summary with conditional formatting, and a custom patient-level Excel file, none of which a native subscription offers. Criteria: General guide §8.

### 4.1 DAX queries

All three queries use the same semantic model:

| Field | Value |
|---|---|
| Workspace (`groupid`) | `bda5d4e4-139b-44fb-880a-835f2bbeee87` |
| Semantic model (`datasetid`) | `40c5834f-4047-45b3-9df6-1161b56ad07b` |
| Table | `pvw_ops_hh_noticeofadmission` |
| Measures used | `[# Cases]`, `[Overdue]`, `[Today]`, `[Due in 1 Day]`, `[Due in 2 Days]`, `[Due in 3 Days]` |

**Query 1: overall summary** (returns a single row).

```dax
EVALUATE
SUMMARIZECOLUMNS(
    "# Cases",       COALESCE([# Cases], 0),
    "Overdue",       COALESCE([Overdue], 0),
    "Due Today",     COALESCE([Today], 0),
    "Due in 1 Day",  COALESCE([Due in 1 Day], 0),
    "Due in 2 Days", COALESCE([Due in 2 Days], 0),
    "Due in 3 Days", COALESCE([Due in 3 Days], 0)
)
ORDER BY [# Cases] DESC
```

**Query 2: patient-level detail** (one row per NOA; it has no filter, so it returns the whole table).

```dax
EVALUATE
SELECTCOLUMNS(
    'pvw_ops_hh_noticeofadmission',
    "Branch",          'pvw_ops_hh_noticeofadmission'[Branch Code],
    "Patient Name",    'pvw_ops_hh_noticeofadmission'[Patient Name],
    "MR No.",          'pvw_ops_hh_noticeofadmission'[MR No.],
    "Payor Source",    'pvw_ops_hh_noticeofadmission'[Payor Source],
    "SOC Date",        'pvw_ops_hh_noticeofadmission'[SOC Date],
    "Visit Completed", 'pvw_ops_hh_noticeofadmission'[SOC Visit Completed],
    "Visit Status",    'pvw_ops_hh_noticeofadmission'[SOC Visit Status],
    "Due Date",        'pvw_ops_hh_noticeofadmission'[Due Date],
    "Days",            'pvw_ops_hh_noticeofadmission'[Adjusted Days Remaining],
    "Due",             'pvw_ops_hh_noticeofadmission'[Bucket]
)
ORDER BY [Days] ASC, [Due Date] ASC, [Branch] ASC, [Patient Name] ASC
```

**Query 3: totals by branch.**

```dax
EVALUATE
SELECTCOLUMNS(
    SUMMARIZECOLUMNS(
        'pvw_ops_hh_noticeofadmission'[Branch Code],
        "# Cases",       COALESCE([# Cases], 0),
        "Overdue",       COALESCE([Overdue], 0),
        "Due Today",     COALESCE([Today], 0),
        "Due in 1 Day",  COALESCE([Due in 1 Day], 0),
        "Due in 2 Days", COALESCE([Due in 2 Days], 0),
        "Due in 3 Days", COALESCE([Due in 3 Days], 0)
    ),
    "Branch",        [Branch Code],
    "# Cases",       COALESCE([# Cases], 0),
    "Overdue",       COALESCE([Overdue], 0),
    "Due Today",     COALESCE([Today], 0),
    "Due in 1 Day",  COALESCE([Due in 1 Day], 0),
    "Due in 2 Days", COALESCE([Due in 2 Days], 0),
    "Due in 3 Days", COALESCE([Due in 3 Days], 0)
)
ORDER BY [Overdue] DESC, [Due Today] DESC, [Branch] ASC
```

### 4.4 Office Script `NOA_report.osts`

Stored in SharePoint at `/Power BI/Team Documents/Report Documentation/Home Health/NOA Subscription Email Files/Templates/NOA_report.osts` and run by step 14 against the day's `NOA_yyyyMMdd.xlsx`. It returns nothing to the flow.

**Parameters**

| Parameter | Type in the script | Default | Value sent by the flow | Meaning |
|---|---|---|---|---|
| `records` | `string` | (required) | `outputs('Compose_Data_for_script')`, the step 5 array | Patient-level rows as JSON. The script runs `JSON.parse` on it |
| `dueColumnName` | `string` | `"Due"` | `"Days"` | Name of the table column that drives the highlighting. Matched case-insensitively and ignoring surrounding spaces |
| `formatScope` | `"cell"` or `"row"` | `"cell"` | `"row"` | `"cell"` highlights only the driving column; `"row"` highlights the whole row |

**What it does, in order**

1. Gets the table `tblNOA`. If it does not exist, it stops with the error `Table 'tblNOA' not found in the workbook.`
2. Parses `records` and maps each record to a 10-value row in this fixed order: `[Branch]`, `[Patient Name]`, `[MR No.]`, `[Payor Source]`, `[SOC Date]`, `[Visit Completed]`, `[Visit Status]`, `[Due Date]`, `[Days]`, `[Due]`.
   - A missing or `null` property becomes an empty cell (`?? ""`).
   - `[Days]` goes through `toNumber`: numbers (including decimals) are written as numbers; empty or non-numeric values become an empty cell, not 0.
   - `[Due]` (the bucket, for example "PENALTY UP TO 7%") stays as text.
   - Dates (`SOC Date`, `Due Date`) are written as the strings the connector returned. The script does not convert them, so how they display depends on the string format and on the template's column formatting.
3. Deletes every existing data row of `tblNOA`, so it is safe to rerun on the same workbook.
4. If there is at least one record, it appends all rows in one `addRows` call and then applies the conditional formatting. If there are no records, the table is left empty and no formatting is applied.

**Conditional formatting**

The script first clears all conditional formats on the target range, then adds two rules. With the flow's settings (`formatScope = "row"`, `dueColumnName = "Days"`), the target is the whole data body of `tblNOA`, and each rule is a formula anchored on the `Days` column with an absolute column and relative row (for example `$I2` when `Days` is column I):

| Rule | Formula (row mode) | Format | Meaning |
|---|---|---|---|
| 1 | `=AND(ISNUMBER($I2),$I2<0)` | Bold, red `#C00000` | NOA is already late (negative days remaining) |
| 2 | `=AND(ISNUMBER($I2),$I2=0)` | Bold, orange `#ED7D31` | NOA is due today |

`ISNUMBER` keeps rows with an empty `Days` value unformatted. In `"cell"` mode the script would instead add two cell-value rules (`< 0` and `= 0`) only on the driving column. Because these are conditional formats, the highlighting stays correct if someone sorts or filters the attachment.

**Assumptions the workbook template must meet**

`Templates/Admissions_Template.xlsx` must contain:

- A table named exactly `tblNOA`.
- **Exactly 10 columns, in the order listed in step 2.** The script writes values by position, not by header name, so an extra, missing or reordered column either makes `addRows` fail or puts data under the wrong header.
- A column whose header is `Days` (any case), the one named by `dueColumnName`. Otherwise the script stops with `Column 'Days' not found in table 'tblNOA'.`
- A total row is optional: the script only touches the range between the header and the total row.

**Limits that apply** (Office Scripts platform limits): 120 seconds per run, 5 MB per request to Excel (the single `addRows` call carries all rows), 28.6 MB of parameters, and 1,600 runs per user per day. At about 10 short columns per row, the volume of a daily NOA list stays far below these limits.

## 7. Error handling

- **Try/Catch/Finally structure:** none. Every action depends on the previous one finishing as `Succeeded`.
- **Failure notification:** only Power Automate's automatic alert to the owner. The package has `failureAlertSubscription: true` in the metadata but `flowFailureAlertSubscribed: false` in the properties, so confirm it in the portal.
- **Retries:** the connector's default policy on every action; none is customized.
- **Covered and uncovered cases:**

| Case | Covered? | What happens today |
|---|---|---|
| Model refresh fails or runs past 9:50 (it normally ends at 9:35) | No | Yesterday's data is sent without warning (F11) |
| A detail field arrives empty | No | `includeNulls: false` drops the property, `Parse JSON` fails because every field is required, and **no email is sent** (F3). The script itself would handle it: it writes an empty cell |
| `Adjusted Days Remaining` has decimals | No | `Parse JSON` fails because `[Days]` is typed as `integer`. The script itself would accept decimals |
| No pending NOAs | Yes | The summary shows zeros; the script empties `tblNOA` and skips formatting; the email is sent with an empty attachment |
| `tblNOA` missing, renamed or with different columns in the template | No | The script throws an error or writes data under the wrong headers (F17) |
| Query truncated by the row limit | No | An incomplete detail is sent without warning |
| The script takes longer than 120 s | No | The action times out and no email is sent |
| A second run on the same day | No | `Create_file` tries to create a file whose name already exists (F6) |

## 9. Security and health data

- **Classification of the data sent:**
  - Email body: **aggregates only** (totals and counts by branch). No identifiable data.
  - Excel attachment: **PHI**. It includes patient name, medical record number (MR No.), payer source, start of care date, visit status and due date.
- **Minimization:** the Excel file with the detail for **all** branches goes to **all** branch office staff. Each person receives data on patients from branches they do not serve. This conflicts with the HIPAA "minimum necessary" standard ([45 CFR 164.502(b)](https://www.ecfr.gov/current/title-45/subtitle-A/subchapter-C/part-164/subpart-E/section-164.502)). See F1.
- **Secure inputs/outputs:** **off on every action.** The run history stores patient-level detail in steps 4, 5, 6, 13, 14 and 22, visible to any owner or co-owner of the flow. See F2 and General guide §7.5.
- **External recipients:** none; all domains belong to the organization. Even so, the attachment has no sensitivity label and no Microsoft Purview encryption.
- **Persistent copy:** every run leaves a `NOA_yyyyMMdd.xlsx` with PHI in the BI documentation folder in SharePoint. The flow never deletes them, so they pile up under whatever permissions that library has.
- **Row-level security (RLS):** the query runs as Ralf Brubacher. If that account can see every branch, the flow sends every branch to everyone, regardless of the RLS that applies to each recipient in the report.
- **Applicable regulation:** HIPAA (Privacy Rule and Security Rule), as a US healthcare provider.

Criteria: General guide §7.5 and §7.6.
